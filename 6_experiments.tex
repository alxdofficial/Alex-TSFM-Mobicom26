\subsection{Methodology}
\label{sec:methodology}

We ask four questions. \textbf{(Q1)} Along the label-efficiency curve---$k$ target
exemplars per class, for $k$ from zero up to full supervision---where does HALO stand against
strong frozen encoders, and is there a regime it owns? \textbf{(Q2)} Does the tokenizer's inductive bias do
what Section~\ref{sec:no_grammar} claims---is the representation genuinely rate-invariant, is
the conditioning too coarse to identify a corpus, and, decisively, does anchoring let one flat
memory serve devices it was not built from? \textbf{(Q3)} Which Phase-A
objectives carry the transfer, and does any of them beat its own untrained control?
\textbf{(Q4)} Does the system run on a phone, and does it behave in a real deployment?

\subsubsection{Data}
\label{sec:datasets}

We train on 12 public HAR datasets contributing 20 distinct sensor streams
(Table~\ref{tab:datasets}, top), and evaluate on 7 datasets never seen by any model during
training (bottom). After conversion to native-rate grids and the removal of 95 windows whose
values exceed physically possible sensor rails, the corpus is $343{,}140$ non-overlapping
six-second windows---$572$ hours of signal---over $93$ activity labels, split subject-disjointly
into $300{,}231$ training and $42{,}909$ validation windows. The validation split is constructed by a greedy label-cover procedure so
that all $93$ labels are represented.

\subsubsection{Baselines and the fairness contract}
\label{sec:baselines}

Cross-model comparison in this setting is easy to get wrong, because the models do not accept
the same inputs. We therefore state a single contract and apply it uniformly
(Table~\ref{tab:baselines}). Each model occupies a \emph{level} on each of four tiers---base
architecture, sampling rate, channels/placement, and label vocabulary---and we never modify a
released checkpoint's input contract, because doing so discards the model being tested. Two
baselines (CrossHAR, LiMU-BERT) release no checkpoint compatible with our corpus, so we
pretrain them ourselves on \emph{our} training data with their own published objectives, which
makes their data identical to ours; three (harnet, UniMTS, NormWear) are used as released,
which is faithful but means their pretraining corpora differ from ours and from each other.
This distinction is material---harnet is pretrained on roughly $700$k person-days against our
$\sim\!570$ hours of windowed signal---and we state it wherever a comparison could be read as a like-for-like
data-matched result. Closed-vocabulary models are bridged to arbitrary label strings with
ConSE~\cite{conse}, which projects a classifier's softmax over its training labels into the
text-embedding space, so that ``can predict an unseen label'' is available to every model and
is not something HALO is credited for.

\subsubsection{Protocol}
\label{sec:eval_protocol}

\emph{Scoring.} Following the good-practice arguments of the zero-shot evaluation
literature~\cite{zslgbu}, every held-out dataset is scored against its \emph{own} label
strings, never a shared training-wide ontology, so a prediction counts only if it retrieves that dataset's exact
activity name. Macro-F1 is primary, with accuracy alongside, because held-out label
distributions are imbalanced.

\emph{Splits.} All few-shot fits and all memory writes use subjects disjoint from those
evaluated. Where a cohort is small enough that a single split is unstable, we rotate over
grouped folds and report a confidence interval.

\emph{Label leakage.} The label-text ensemble used at inference is purged of synonyms drawn
from the evaluation datasets, so that no evaluation vocabulary is smuggled in through
paraphrase. Retrieval hyper-parameters are selected on held-out \emph{training} configurations,
never on evaluation cells.

\emph{Parity control.} To separate the architecture from its native-rate and rich-text inputs,
HALO is additionally evaluated under baseline-equivalent inputs: common $20$\,Hz resampling and
a neutral sensor description (Table~\ref{tab:parity}).

\subsection{Q1: The Label-Efficiency Curve}
\label{sec:label_efficiency}

This is the headline experiment. For each held-out dataset and each budget $k$ of labelled
target windows per class, we compare three mechanisms on identical data: HALO's memory, given
the $k$ exemplars as an append with \emph{no gradient update}; a probe fitted on the same $k$
exemplars over HALO's frozen features; and the same probe over frozen harnet features, which
is the strong-representation control. We additionally report \emph{retrieval over harnet
features}---the same memory mechanism on a different encoder---because without it a win could
be attributed to the mechanism when it belongs to the representation, or the reverse.

\textbf{Pre-registered hypothesis and kill criterion.} We expect retrieval to win at small $k$,
where a nearest-neighbour decision beats a linear fit on a handful of points, and the probe to
overtake somewhere between $k{=}10$ and $k{=}50$. If that holds, the regime HALO owns is
$k \le 10$, which is exactly the enrollment setting a user can perform in under a minute. If
the probe dominates at \emph{every} $k$ including $k{=}1$, retrieval has no regime of its own;
we will report that outcome plainly.

\subsection{Q2: Does the Inductive Bias Do What It Claims?}
\label{sec:bias_experiments}

Section~\ref{sec:no_grammar} made two falsifiable claims about the tokenizer. Both are tested
directly rather than inferred from end-task accuracy.

\textbf{Rate-invariance is measured, not assumed.} A closed-form check confirms that a pure
tone deposits identical band energies at $20$, $50$, and $100$\,Hz, and that changing the DFT
padding from $S{=}256$ to $512$ leaves band energies and masks unchanged. The end-task version
of the claim is Table~\ref{tab:tokenizer_ablation}: the same encoder trained on the same data
but reading a common $20$\,Hz resampling of every stream. This is the experiment that
distinguishes a physical-frequency \emph{anchoring} from mere resolution flexibility---if the
$50$ and $100$\,Hz streams carry discriminative content above $10$\,Hz, resampling must destroy
it, and the gap is the measurement of how much.

\textbf{Does anchoring actually make one cross-device memory well-posed?} This is the
experiment that decides whether HALO is an assembly of known parts or an enabling result, so we
state it precisely. A flat memory shared across devices is only meaningful if a query encoded
from one configuration retrieves useful neighbours stored from a \emph{different}
configuration. Table~\ref{tab:crossconfig} measures exactly that: rows are the configuration a
query comes from, columns the configuration the memory is restricted to, and cells report
retrieval quality. The diagonal is same-configuration retrieval, which every system can do; the
off-diagonal is the claim.

The measurement is unusually clean because parts of our corpus contain \emph{verified
simultaneous} recordings---the same person performing the same activity at the same instant,
captured by two or more devices at different placements (XRF~V2 at six placements, SP-SW-HAR
phone and watch, NFI-FARED wrist and lower back, WISDM pocket and watch). Querying with one
stream against a memory built only from its simultaneous partner isolates acquisition
configuration from subject, session, and activity entirely: any degradation off the diagonal is
attributable to the configuration change and to nothing else. We report the same matrix for a
resample-to-common-rate variant of our own encoder, and for the frozen baselines, so that the
comparison is of mechanisms rather than of corpora.

\textbf{Is the naive assembly enough?} The components HALO uses have individually appeared
before: variable channel counts, variable rates, and language-mediated label interfaces all
have prior solutions. The claim that they must be assembled \emph{this particular way} is
therefore an empirical one, and Table~\ref{tab:tokenizer_ablation} includes the obvious
alternative assembly as a row: resample every stream to a common rate, attach free text per
channel, and put the same retrieval mechanism on top. If that arm matches HALO, the
architecture is a combination and we will say so; the mutual-entailment argument of
Section~\ref{sec:combination} predicts it will not, and predicts a specific reason---the
per-channel conditioning should show up as elevated dataset identifiability in
Table~\ref{tab:identity_probe}, and the resampling should show up as a rate gap in
Table~\ref{tab:tokenizer_ablation}.

\textbf{Conditioning must not be a corpus fingerprint.} Table~\ref{tab:identity_probe} reports
a dataset-identity probe: a linear classifier fitted on frozen embeddings to predict which
\emph{source dataset} a window came from, on held-out subjects. A representation that has
absorbed the acquisition description as a corpus identifier will make this easy; one whose
conditioning is genuinely compositional will not. We report it for HALO's factored per-sensor
conditioning, for a per-channel free-text variant, and for the baselines, and we report it
whether or not it favours us. It is cheap---frozen features and a linear fit---and it is the
only direct evidence we have for the ``too little bias'' failure mode.

\subsection{Q3: Which Phase-A Objectives Carry the Transfer?}
\label{sec:objective_ablation}

Each Phase-A term is removed independently with all others held fixed
(Table~\ref{tab:objective_ablation}). Two controls matter more than the ablation itself. First,
the \emph{untrained control}: the evidence decoder is identity-at-initialisation by
construction, so for every trained arm we report the same architecture untrained; a trained
component that does not beat its own initialisation is reported as such. Second, the
\emph{label-supervised control}: the original supervised recipe (masked prediction $+$
label-SupCon $+$ grounding rail) remains selectable, so the claim that going fully label-free
helps is measured, not asserted.

\subsection{Q4: On-Device Cost and a Real Deployment}
\label{sec:deployment_experiments}
\label{sec:case_study}

\PENDING{On-device latency, peak memory, retrieval cost as a function of memory-bank size, and
the case-study numbers, once the encoder is compiled and profiled.}

We implement the full pipeline as an iOS application and will report: encoder latency and peak
memory under Core~ML; retrieval latency as a function of bank size; and a continuous
case study in which a user enrolls activities by demonstration, changes the device's body
placement mid-session, and introduces activity names that were never enrolled. That case study
is the deployment form of the label-efficiency argument: enrollment by demonstration is what
$k \le 10$ means to a user.
