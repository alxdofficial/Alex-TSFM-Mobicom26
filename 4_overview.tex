\section{System Overview}
\label{sec:overview}

HALO is organised as two phases with a hard boundary between them
(Figure~\ref{fig:overview}). \textbf{Phase~A} learns a representation of inertial signals
using no activity labels whatsoever. \textbf{Phase~B} turns that frozen representation into a
recogniser for whatever label set a deployment declares, using labels only as annotations on
stored exemplars. The boundary is not an implementation convenience; it is where the argument
of Section~\ref{sec:motivation} lands. L1 says compatibility must be structural, so it belongs
in the encoder, before any label is involved. L2 says the label decision must not be a
projection into text space, so it belongs after the encoder, in a component that can be swapped
per deployment.

\textbf{Phase~A: label-free representation pretraining
(Section~\ref{sec:tokenizer_design},~\ref{sec:phaseA_design}).}
A window of raw, native-rate samples---at whatever rate the device runs, with whatever subset of
accelerometer and gyroscope axes it exposes---is grouped into sensors and passed through a
physical-frequency constant-$Q$ filterbank, producing one token per sensor per patch on a
frequency axis that is the same at every sampling rate. Each token is conditioned on natural
language describing the \emph{sensor} it came from, and on per-token masks declaring which
frequency bands that rate and window length could actually observe. A dual-branch transformer
with rotary positions over \emph{physical time} then mixes tokens across time and across
sensors. Training combines masked latent prediction against both a fixed physical target and a
slow EMA teacher, a VICReg objective over independently augmented views, a time--frequency
consistency term, a low-weight consistency term over \emph{verified simultaneous} recordings of
the same physical event at different body placements, and a small self-derived physical
grounding rail. None of these uses an activity label.

\textbf{Phase~B: the evidence engine (Section~\ref{sec:evidence_design}).}
The encoder is frozen. Labelled windows---from the training corpus, from a target deployment,
or both---are encoded once and stored in a memory table together with their label, subject,
acquisition configuration, sensor group, and patch timing. At inference, the query window is
encoded and its patches retrieve neighbours from memory by similarity in \emph{sensor} space.
A decoder then contextualises query and evidence tokens together and accumulates non-negative
evidence for each label string in the run-time candidate set, with a separately estimated
rejection confidence derived from retrieval density, patch and sensor agreement, vote entropy,
and the leading margin. Label text is used to name evidence and to enumerate candidates; it is
never the space in which similarity is computed.

\textbf{One curve, not two regimes.} Because memory is append-only, the amount of target
supervision is a dial rather than a mode. With an empty target memory the system still runs:
evidence comes from corpus exemplars and the candidate strings alone. Appending $k$ demonstrated
windows per class costs one forward pass each and no gradient step, so it is feasible on a phone
and the data need never leave it. When labels are plentiful the frozen representation also
supports conventional supervised fitting. Section~\ref{sec:experiments} therefore reports a
single label-efficiency curve over $k$ rather than separate zero-shot and fine-tuned tables.

\textbf{Scale.} The encoder is $7.17$M trainable parameters ($d{=}256$, $6$ layers; $6.32$M in
the transformer, $0.82$M in text fusion, $25$K in the filterbank), plus one frozen
all-MiniLM-L6-v2 sentence encoder ($22.7$M) shared by sensor conditioning and label text.
Phase-A objective heads add $0.62$M and are discarded at inference. The Phase-B decoder is a
small set transformer over retrieved evidence.

\textbf{Deployment.} A deployment is specified by configuration, not code: a per-sensor
description string and a list of candidate activity names. Both are embedded once and cached, so
run-time cost is one encoder pass plus a retrieval (Section~\ref{sec:deployment}).
