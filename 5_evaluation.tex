\section{Evaluation}
\label{sec:experiments}

This section states the corpus the system is trained on, the enrollment protocol and its controls,
and the measurements that must exist before we make a performance claim. We report no accuracy
number. The Phase-A encoder is complete and its memory and resolvability artifacts are built against
it, but the admissibility gate has not been fitted to those artifacts, so no enrollment result is
attributable to the system this paper describes.

\subsection{Data and Artifacts}
\label{sec:methodology}
\label{sec:datasets}

manifests contain 1,963,606 stream-window rows before quality screens and the subject split. The

\subsection{Evaluation Protocol}
\label{sec:eval_protocol}

An evaluation dataset supplies its own candidate inventory; this is a HALO protocol choice, not a
claim established by the generalized zero-shot-learning benchmark. Following that benchmark, we
separately report whether a candidate was seen or unseen during training~\cite{zslgbu}. Macro-F1 is
primary because activity frequencies are imbalanced.

For enrollment, support and query executions are disjoint. The development evaluation uses
cross-subject cohorts over MotionSense, RealWorld, and Shoaib. At each $k\in\{1,2,4,8\}$, we retain
the same queries and candidate inventory and nest the support prefixes. A verified recording
execution, not an adjacent window, counts as one example. We also run support removal, cyclic
support-label shuffling, an all-one admissibility control, prototypes, and ridge heads on the
identical features and support split. These controls are part of the claim, not optional ablations:
the all-one arm isolates the gate, and the prototype and ridge arms establish what the frozen
representation already supports without any retrieval machinery.

The protocol must include cells in which the enrolled configuration differs from the query
configuration. A two-sided admissibility test scores the query sensor and the evidence sensor
against each candidate; when both are the same sensor, that product reduces to a per-candidate
constant and cannot express configuration dependence at all. Cross-configuration cells are therefore
not an extension of the protocol but a precondition for it to measure the mechanism.

The test roster is fixed: InclusiveHAR, USC-HAD, TNDA-HAR, UT-Complex, MoniPar, SPAR, and Upper Limb
Use. TNDA-HAR has no usable subject-disjoint enrollment cohort and contributes only to a future
zero-support cell. SPAR's repetitions occur within one bout and do not establish across-session
enrollment. MoniPar is the held-out source that can support across-week enrollment. We consume none
of these datasets in the present revision.

\subsection{Required Measurements Before a Performance Claim}
\label{sec:label_efficiency}
\label{sec:pending_measurements}

The following experiments are part of the protocol and do not yet have provenance-complete
artifacts:

\begin{itemize}
  \item development enrollment curves for the gate against every control above, on a bank and gate
        bound to the completed encoder;
  \item cross-configuration enrollment on simultaneous training streams, reported separately from
        the external test result;
  \item held-out concept, dataset, and body-region studies for the gate, including gate-collapse,
        provenance-capture, and latent-to-measurement guards;
  \item native-grid versus common-rate, sensor-folded versus channel-level, descriptor-on,
        acquisition-bias-on, observability-off, and signed-low-frequency ablations;
  \item all-pairs activity-text similarity versus sensor-centroid similarity, replacing any
        hand-selected quantitative geometry claim;
  \item data-matched and released-checkpoint baselines, including the published short fine-tuning
        baseline the wearable-foundation-model literature requires; and
  \item only after the development criteria are met, one evaluation of the seven-dataset sealed test
        roster with confidence intervals and seen/unseen candidate breakdowns.
\end{itemize}

We claim no on-device latency, Core~ML, iOS, or unknown-class result, because the corresponding
implementation and measurement artifacts do not exist in the repository.
